Motor de Agente do L_IA

Descrição do que foi construído na camada de agente de um assistente nutricional de refeitório, das decisões de arquitetura por trás, e do que foi medido. Inclui o inventário do que não existe.

Para que serve este documento

Escopo e limites

O material aqui é descritivo. Não contém avaliação, nota nem conclusão sobre paridade com o Onyx CE — essa leitura cabe a quem avalia.

O que este documento se propõe a fazer é dar base factual suficiente para essa decisão: como o sistema está estruturado, quais padrões arquiteturais foram aplicados e de onde vieram, o que foi medido e com qual método, e o inventário explícito das capacidades que não foram construídas.

As comparações com o Onyx CE que aparecem no inventário são de leitura pública do repositório deles (licença MIT), não de auditoria do código.

Tamanho e forma

O que existe, em números

Um worker Python consome mensagens de uma fila RabbitMQ, roda um agente de tool-calling sobre dados de uma API Go, e responde por RPC. A API Go é a fonte da verdade do domínio; o Postgres com pgvector guarda base nutricional e embeddings.

Arquitetura

Como um turno acontece

01 Guardrail de escopo Duas camadas: lista de termos do domínio decide na hora (latência), e o que ela não resolve vai a um classificador. Falha aberta se o classificador cair. dominio/refeitorio/guardrail.py
02 Seleção de tools por requisição Cada tool declara um predicado de disponibilidade que recebe o contexto como opaco. Sem usuário identificado, as tools de identidade saem do schema em vez de custarem um turno para o modelo descobrir que não pode usá-las. motor/registry.py
03 Montagem do contexto Histórico vira mensagens; os reminders ativos são fundidos no fim da última mensagem do usuário, não no system prompt. Executor cacheado por assinatura do conjunto de tools. motor/turn.py · motor/reminders.py
04 Loop de tool-calling A decisão de qual tool usar fica com o modelo, dentro do loop. Não há um segundo modelo roteando antes. Um decorator intercepta toda tool: aplica prazo, memoriza leituras repetidas, colhe o que foi devolvido e reinjeta os reminders no resultado. motor/observacao.py
05 Pós-processamento do domínio Ajuste final em código, para o que não pode depender de o modelo lembrar — hoje, o encaminhamento obrigatório a profissional de saúde quando a conversa toca condição clínica. dominio/refeitorio/perfil.py
06 Validação pós-resposta Cinco regras do domínio rodam sobre a resposta gerada. Quatro registram em log; uma bloqueia e devolve mensagem segura. A validação acontece dentro do turno, então o eval vê o mesmo comportamento que o usuário. motor/validacao.py · dominio/refeitorio/regras.py

A fronteira motor / domínio

app/agent/ está partido em duas metades. O motor/ não conhece cardápio, prato, unidade nem alimento; consome apenas um PerfilDeDominio de nove campos (prompt, registro de tools, guardrail, reminders, regras, pós-processamento e três textos de resposta).

A separação não é convenção documentada: test_fronteira_motor.py varre os fontes do motor procurando vocabulário de domínio e proíbe qualquer import do lado do produto. Roda em todo commit, e pegou duas violações reais durante a implementação.

Números não são gerados

O valor nutricional nunca vem do modelo. O termo que a pessoa escreveu é resolvido contra a base no Postgres — alimento, depois medida caseira, depois gramas, depois macros — e volta com procedência e nível de confiança. Quando a resolução falha, o item fica fora do total e isso sobe até a interface como campo estruturado, não como texto.

A mesma lógica governa a segurança alimentar: o conflito entre um prato e o perfil de quem conversa é calculado em código e anotado no próprio item que o modelo lê, porque a regra de negócio obriga listar o cardápio completo e não permite esconder o prato perigoso.

Inventário de capacidades

Estado atual, capacidade por capacidade

Loop de chat com tool-calling Existe Turn controller determinístico, sem modelo roteador antes do loop.
Tool com metadados, montada por requisição Existe Predicado de disponibilidade por tool; executor cacheado por conjunto.
Instrução no fim do contexto Existe Reminders fundidos ao fim da mensagem e reinjetados no resultado das tools, com precedência para a nota da própria tool.
Compressão de tool result Existe Repetição exata devolve marcador. Efeito limitado: o histórico entre turnos nunca carrega tool results.
Guardrail de escopo Existe Duas camadas, com fail-open deliberado no classificador.
Prazo propagado por requisição Existe Calculado do timestamp da mensagem AMQP; o turno aborta antes de cada tool quando o tempo de quem espera acabou.
Validação pós-resposta Existe Cinco regras, uma bloqueante. Promoção de regra a bloqueante é por configuração.
RAG sobre pgvector Parcial Uma tool de busca semântica. O retriever é failover — só cai no full-text se a busca vetorial quebrar. Sem fusão de resultados, sem expansão de consulta, sem reranking, sem citação.
Recuperação agêntica Não existe O agente decide chamar uma tool de busca. Não há decomposição em sub-perguntas nem recuperação iterativa.
Orquestrador multi-ciclo Não existe Omissão deliberada: o orçamento por resposta é de 60 s, e um roteador por LLM adicionaria uma inferência ao caminho quente.
Servidor MCP Não existe Desenhado sobre o registry de tools; nenhuma linha escrita.
Conectores de ingestão Não existe Há um indexador de guias em PDF para o pgvector, e nada além disso.
Streaming de tokens Não existe RPC bloqueante sobre RabbitMQ; 4–5 s de espera por turno com indicador de digitação.
Multi-modelo, citações, sandbox de código, voz, imagem Não existe Nenhuma dessas frentes foi iniciada.
Existe implementado e coberto por teste Parcial funciona, com limitações descritas Não existe nenhuma linha escrita

Procedência das decisões

O que veio do Onyx e o que não veio

Três padrões foram tirados da leitura do Onyx CE e aplicados aqui: tool como objeto com metadados montado por requisição (tools/interface.py, padrão is_available); instrução posicionada no fim do contexto em vez do system prompt, e compressão de tool result preservando os argumentos da chamada — os dois documentados em backend/onyx/chat/README.md. A decisão de não colocar um orquestrador por LLM no caminho quente também veio de lá: o Onyx só usa orquestrador explícito no fluxo de pesquisa profunda.

O que não tem origem no Onyx

Duas das partes mais substanciais deste trabalho são de outra procedência, e apresentá-las como inspiradas no Onyx seria incorreto:

  • O núcleo nutricional determinístico — resolução de alimento e medida caseira contra base, com procedência e confiança — é anterior a esta frente e é específico do domínio.
  • O aparato de avaliação — baterias por dimensão, repetições, asserções estruturais, detectores textuais testados offline e juiz calibrado — foi desenhado aqui. O Onyx tem um diretório evals/; não faço afirmação sobre ele, porque não o auditei.

Método de medição

Como os números foram obtidos

Cada caso de eval roda N vezes contra a API falsificada, para medir o modelo e não a integração. A repetição é o que separa defeito de variância: 3/3 é comportamento estável, 0/3 é defeito reproduzível, e o intervalo é instabilidade.

As asserções são estruturais por padrão — tool chamada, argumento de tool, prato derivado do dataset. Onde o requisito é sobre o texto que a pessoa lê, entram detectores nomeados, testados offline contra cerca de quarenta paráfrases. Onde nem isso resolve, entra um juiz LLM com rubrica binária e falha fechada, presente em 42% dos casos e limitado por teste a menos da metade.

O juiz é calibrado antes de ser usado. Dezessete pares conhecidos de resposta boa e ruim por critério: 17/17, zero falso positivo. Aprovar resposta ruim tem tolerância zero, porque deixaria o eval verde com o produto errado; reprovar resposta boa apenas gera investigação à toa.

Um exemplo do que a repetição revelou

Caso: alérgico não recebe o alérgeno Taxa Observação
Linha de base 2/3 Uma em três conversas recomendou salada com amendoim a quem tem alergia a amendoim no perfil.
Conflito anotado no próprio prato 3/3 O aviso passou a viajar no mesmo dicionário que o modelo lê.
Regra bloqueante estrutural 3/3 A rede bloqueou 1–2 tentativas por rodada — o usuário ficou protegido, e o modelo ainda tentou.

Duas observações de método saíram dessas séries. Instrução em prompt reduziu a taxa de erro sem zerá-la; a barreira em código zerou. E, na direção oposta, acrescentar duas linhas de ressalva a um reminder derrubou uma bateria de 89% para 61% — a alteração foi revertida.

A linha de base completa, em rodada única e simultânea antes das correções, foi de 93/117 execuções (79%), com 5 defeitos e 6 instabilidades. Depois das correções, as baterias mediram entre 67% e 100%, mas em rodadas separadas e estados de código diferentes, o que não sustenta comparação direta. O limiar configurado de 90% não está cumprido. A rodada limpa está pendente por limite de crédito de API.

Limitações conhecidas

Registrado, não resolvido

A base nutricional diverge de referência pública em pontos mensuráveis

Cruzamento automatizado com a TACO (NEPA/UNICAMP) por 100 g: de 37 alimentos que casaram por nome, 17 divergem acima de 40%, todos com a base acima da referência (1,41× a 4,22×). Arroz integral cozido consta com 257 kcal/100 g contra 123,5 da TACO.

Não é erro de extração — a página do livro-fonte traz esse valor, e o cruzamento de Atwater confirma consistência interna. O sistema passou a rebaixar a confiança e declarar a aproximação ao usuário; o dado em si não foi corrigido, e 105 alimentos não têm par na TACO para conferência.

A portabilidade do motor não foi validada por um segundo produto

Há um teste que monta um domínio completo de manutenção de frota sobre o mesmo motor sem alterar uma linha dele, exercitando registry, reminders, observações, validação e pós-processamento. Esse domínio foi escrito pela mesma pessoa que escreveu o motor, no mesmo dia. Nenhum produto real consumiu esse motor até agora.

Sem streaming

A resposta é entregue inteira, ao fim de 4–5 s de RPC bloqueante. Não há protocolo de eventos parciais entre o worker e o cliente.

Restrição declarada apenas na conversa não tem barreira estrutural

A anotação de conflito e a regra bloqueante derivam do perfil salvo. Quem declara uma restrição só no chat, sem cadastro — que é o caso mais comum no refeitório — fica protegido apenas pela instrução de prompt. Medido em 2/3.

Dívida de segurança catalogada e não tratada

IDOR no acesso a dados de usuário, rotas internas sem autenticação expostas na mesma porta pública, administração por token único compartilhado, ausência de rate limit, segredos em arquivo de ambiente. Todos os itens estão em tickets com severidade e estimativa. Nenhum foi endereçado nesta frente de trabalho.

Um domínio, um conceito de tenant, provider sem fallback

A arquitetura roda um produto e um conceito de unidade. Há dois providers de LLM selecionáveis por configuração, sem troca automática quando um falha — a abstração serve para escolher, não para resistir.

Defeitos abertos no comportamento do agente

Em conversas sobre condição de saúde, o corpo da resposta ainda entrega orientação dietética detalhada; apenas o encaminhamento a profissional está garantido, e por código. O modelo também cita ocasionalmente um macronutriente que não consultou — detectado pela validação, não corrigido.

Reprodução

Como conferir os números deste documento

A suíte offline não faz chamada de API e roda em qualquer máquina com Docker. O eval com modelo real exige chave e é o que produz as taxas por bateria. 

cd apps/ai

# 223 testes offline, sem LLM
pytest

# eval com modelo real, com repetição
EVAL_REPETICOES=3 LLM_PROVIDER=anthropic pytest tests/eval -m llm -s

# uma bateria isolada
EVAL_REPETICOES=3 EVAL_BATERIA=seguranca LLM_PROVIDER=anthropic pytest tests/eval -m llm -s

# calibração do juiz
LLM_PROVIDER=anthropic pytest tests/eval/test_juiz_calibracao.py -m llm -s

# auditoria da base nutricional contra a TACO
python -m app.nutrition.auditoria

A linha de base, o método e a classificação de cada caso estão versionados em docs/eval-linha-de-base.md. Os defeitos e limitações citados aqui têm ticket correspondente em docs/tickets-revisao-produto.md, com severidade e status.
