01 Visão de alto nível: as 3 camadas

Onde mora cada peça do sistema
💡 Em uma frase: Um app de chat com IA tem três grupos de peças que conversam entre si: a tela (browser), o servidor (cérebro do app) e o LLM (a "IA" propriamente). E você escolhe se a IA roda na sua máquina ou na nuvem.
🔧 Tecnicamente: Browser (React) fala HTTP com o backend (FastAPI). O backend orquestra guardrail → agent → memória e fala com um LLM via LangChain. O provider é escolhido por env var (LLM_PROVIDER=ollama|anthropic). As tools acessam o cardapio.json de forma determinística (Python puro, não LLM).

O que olhar

  • O backend não fala com o LLM direto — fala via agent.py, que abstrai os providers
  • Tools são funções Python normais; o LLM só decide quando chamar
  • O cardapio.json é a "fonte da verdade" — o LLM nunca inventa pratos

02 O loop interno do Agent

A parte "mágica" do tool calling — explicada
💡 Em uma frase: O LLM não executa código — ele pede pra alguém executar. É como um chef que escreve "faça uma tigela de salada" no papel e entrega pro ajudante: o chef não pega a faca; o ajudante pega, faz, e devolve a tigela pro chef apresentar.
🔧 Tecnicamente: O LLM gera um JSON com {name, args} declarando qual tool quer chamar. O LangChain executa a função Python, anexa o resultado como ToolMessage (uma "mensagem especial" no histórico que diz "isto é o resultado da tool X"), e devolve o histórico atualizado pro LLM. Loop até o LLM gerar texto puro (resposta final). No nosso caso, geralmente 2 voltas: 1 pra decidir, 1 pra formatar.

O que olhar

  • O LLM nunca roda código — só decide
  • O LangChain orquestra o ciclo "LLM → tool → LLM → ..."
  • Quando o LLM responde sem pedir tool, é o fim do loop

03 Anatomia de uma Tool

Decorator, docstring, body — três papéis distintos
💡 Em uma frase: Uma "tool" é só uma função Python comum, mas com um decorador especial em cima dela. O LLM lê o nome, os parâmetros e a explicação (docstring) — mas nunca o código de dentro. É o manual e a etiqueta da função, não o conteúdo.
🔧 Tecnicamente: O decorator @tool do LangChain transforma a assinatura tipada da função em um schema JSON consumível pelo LLM. A docstring serve como "manual de uso" — o LLM lê pra decidir quando chamar. O corpo é caixa-preta para o modelo (boa prática de segurança).

O que olhar

  • Reescrever a docstring → muda o comportamento da IA (ela lê pra decidir)
  • Tipos da assinatura viram schema automaticamente
  • O corpo é caixa-preta pro LLM: ele não pode "manipular" código que não vê

04 Sequência completa de uma mensagem

Caminho feliz: do clique até a bolha de resposta
💡 Em uma frase: Acompanhe o caminho de uma única pergunta — desde o usuário apertar Enter até a resposta aparecer no chat. É como ver o pedido de um restaurante passar pela cozinha inteira.
🔧 Tecnicamente: Um POST /chat dispara: guardrail (filtra escopo) → agent (chama LLM com schema das tools) → tool (Python filtra cardápio em ~0ms) → LLM novamente (formata resposta) → JSON de retorno. Note que o filtro vegetariano roda em código Python, não no modelo.

O que olhar

  • O guardrail bate keyword "vegetariano" e responde em ~0ms — sem chamar LLM
  • O LLM #1 decide: "vou chamar filtrar_pratos"
  • A tool roda em Python e devolve só os pratos que passam no filtro
  • O LLM #2 formata a resposta natural em português

05 Memória de conversa

RAM por session_id, janela de 6 mensagens (3 turnos)
💡 Em uma frase: Cada usuário tem uma "caixinha" separada na memória do servidor com o histórico das últimas mensagens. Reiniciou o servidor, perdeu o histórico — é tipo bilhete na mesa, não livro de cabeceira.
🔧 Tecnicamente: Dict em RAM indexado por session_id (gerado no frontend e salvo em localStorage). Janela de 6 mensagens (3 turnos) limita o crescimento do prefill em CPU. Volátil por design no MVP — SQLite seria o próximo passo pra persistência.

O que olhar

  • A janela de 6 limita o custo do LLM em conversas longas
  • Sessão por session_id garante isolamento entre usuários
  • Botão "Nova Conversa" → DELETE no backend + novo session_id no front

06 Guardrail em duas camadas

Por que prompt sozinho não basta
💡 Em uma frase: Como impedir que a IA fale sobre coisas fora do tópico (receita de bolo, política, "ignore suas instruções"). Você não confia só no prompt — adiciona um filtro estrutural antes de passar a pergunta pro LLM.
🔧 Tecnicamente: Heurística por keywords (~0ms, instantânea) + classificador LLM como fallback (~500ms, só pra casos ambíguos). Combinação cobre ~90% das mensagens sem chamar o classificador. Política fail-closed (se algo quebrar, fica no estado seguro = recusar): se o Ollama cai, recusa por padrão (nunca abre brecha).

Por que duas camadas?

  • Keyword é instantânea, mas não cobre todas as variações de pergunta válida
  • LLM cobre o resto, mas é caro chamar pra TODA mensagem
  • Combinando: 90% não chega no LLM. Só os ambíguos pagam o custo

07 Pipeline de observabilidade

Cada etapa loga seu tempo — saber onde vai o tempo é parte do trabalho
💡 Em uma frase: Cada etapa do processamento gera uma linha de log com o tempo que levou. Quando alguém disser "tá lento", você não chuta — você abre os logs e vê exatamente onde o tempo foi gasto.
🔧 Tecnicamente: BaseCallbackHandler (função que o LangChain "chama de volta" em momentos específicos) do LangChain captura on_chat_model_start/end e on_tool_start/end. Middleware HTTP (filtro que toda request passa antes de chegar no handler) do FastAPI mede o handler completo (entry → response built). Logs estruturados com timestamp permitem cruzamento end-to-end de uma request.

O que olhar

  • Cada linha responde uma pergunta diferente: "qual tool foi chamada?", "o LLM #1 ou #2 demorou mais?"
  • O tempo entre REQ END e HTTP RESP revela overhead de Pydantic/uvicorn (geralmente <1ms)
  • O middleware é o ponto FINAL — qualquer atraso depois disso é rede ou frontend

08 Flow do Docker Compose

4 serviços que sobem em ordem específica
💡 Em uma frase: Um arquivo (docker-compose.yml) descreve quatro "computadores virtuais" (containers) e a ordem em que eles devem subir: primeiro a IA, depois o setup que baixa o modelo, depois o backend, depois o frontend.
🔧 Tecnicamente: depends_on.condition garante a ordem por healthcheck (não só timing). ollama-init roda uma vez e encerra (restart: "no"). Volume nomeado ollama_data persiste o modelo de 2 GB entre down/up. Política restart: "no" evita auto-start no boot.

O que olhar

  • depends_on.condition garante a ordem (não é só "espera 5s")
  • ollama-init roda uma vez e encerra (restart: "no")
  • Volume mantém o modelo entre down/up

09 Lifecycle: prewarm e reprewarm

Como o Ollama fica "quente" no momento certo
💡 Em uma frase: Como deixar a IA "preparada" antes do usuário pedir — pré-aquecer enquanto o servidor está subindo, e re-aquecer quando o usuário clica "Nova Conversa". É tipo ligar o forno antes de começar a cozinhar.
🔧 Tecnicamente: Em CPU, llama3.2 leva ~30s pra processar o system prompt + tools schema (cold start do KV cache — a "memória interna" do LLM ainda não tem nada útil). prewarm() roda em thread daemon (trabalhador silencioso em paralelo) no startup, populando o cache em background. Reprewarm dispara no DELETE /chat/{id}, aproveitando o intervalo "humano pensando". Pulado quando provider=anthropic (sem cold start).

O que olhar

  • Prewarm roda em threading.Thread(daemon=True) — não bloqueia o healthcheck do Docker
  • Reprewarm dispara no handler do DELETE — sem custo aparente pro usuário
  • Para Anthropic, ambos são pulados (provider=anthropic, sem cold start)

10 Adapter dual de provider

Ollama local vs Claude API — uma env var de distância
💡 Em uma frase: Um se/senão que decide se a IA é a local (gratuita, mas mais lenta) ou a Claude (paga, mas muito mais rápida). Pra trocar, você só edita um arquivo de configuração — o resto do código nem sabe que mudou.
🔧 Tecnicamente: _build_llm() em agent.py retorna ChatOllama ou ChatAnthropic conforme a env var. Ambos herdam de BaseChatModel (a "tomada padrão" do LangChain — qualquer LLM implementa a mesma interface) — interface idêntica. O create_agent(), as tools, o guardrail, o frontend continuam intactos. Trocar provider: editar .env + rebuild do backend.

O que olhar

  • Mesma interface (ChatOllama e ChatAnthropic herdam de BaseChatModel)
  • Ollama: ~30s/turno em CPU, gratuito, privado
  • Anthropic Haiku: ~3s/turno, ~R$ 0,01/turno, qualidade superior
  • Prewarm faz sentido só pro Ollama (Anthropic não tem cold start)

11 LangChain vs LangGraph — quando usar cada um

Agent loop linear vs grafo de estado ramificado
💡 Em uma frase: LangChain é tipo seguir uma receita linear: pergunta → tool → resposta. LangGraph é tipo um diagrama de fluxo cheio de "se isso, faz aquilo" — mais poderoso pra fluxos complexos, mas exagero pra casos simples. Comece com LangChain. Migre quando o `create_agent` deixar de caber no problema.
🔧 Tecnicamente: O create_agent() do LangChain encapsula o loop padrão (LLM decide → executa tool → LLM responde). O LangGraph oferece um StateGraph com nós e arestas condicionais — você desenha o workflow em código e tem controle total. LangGraph é construído sobre LangChain — não substitui, é uma camada acima pra workflows ramificados, multi-agente, ou que precisam de checkpoints/human-in-the-loop.

Para a Lia (este projeto)

  • LangChain basta — o ciclo é simples (LLM → tool → LLM → resposta)
  • Migrar pra LangGraph só faria sentido se adicionássemos: confirmação humana antes de finalizar pedido, multi-agente (recomendador + nutricionista), hand-off pra humano
  • Não comece com LangGraph "porque parece mais profissional" — é over-engineering pra MVP

🔶 LangChain — 5 linhas que resolvem
from langchain.agents import create_agent
from langchain_ollama import ChatOllama

llm = ChatOllama(model="llama3.2")
agent = create_agent(
    model=llm,
    tools=TOOLS,
    system_prompt=SYSTEM,
)

# uso
resposta = agent.invoke({
    "messages": [HumanMessage("o que tem hoje?")]
})
🔷 LangGraph — equivalente verboso
from langgraph.graph import StateGraph, END
from langgraph.prebuilt import ToolNode
from typing import TypedDict, Annotated

class State(TypedDict):
    messages: Annotated[list, add_messages]

llm = ChatOllama(model="llama3.2").bind_tools(TOOLS)

def chamar_llm(state: State):
    msgs = [SystemMessage(SYSTEM)] + state["messages"]
    return {"messages": [llm.invoke(msgs)]}

def precisa_tool(state: State):
    return "tools" if state["messages"][-1].tool_calls else END

graph = StateGraph(State)
graph.add_node("llm", chamar_llm)
graph.add_node("tools", ToolNode(TOOLS))
graph.set_entry_point("llm")
graph.add_conditional_edges("llm", precisa_tool)
graph.add_edge("tools", "llm")
agent = graph.compile()
